# Многостраничный сайт: что меняется по сравнению с лендингом

Конвейер тот же (брифы → шлюз 1 → структура → направления → шлюз 2 → юрисдикция → реализация → деплой → QA). Меняется то, что в лендинге было «блоками одной страницы»: теперь это **карта сайта, шаблоны страниц и общие компоненты**. Всё остальное — юридика, форма, админка, деплой — работает как в основном скилле.

## Когда это многостраничник, а не лендинг

Лендинг — одна страница, одно действие. Многостраничник нужен, когда:
- несколько разных услуг/продуктов, каждому нужна своя страница (и своя поисковая выдача);
- есть блог, новости, каталог, портфолио с отдельными карточками;
- трафик приходит из поиска (SEO), а не только из рекламы;
- аудитории разные и им нужны разные пути (частным лицам — одно, бизнесу — другое).

Если пользователь просит «сайт», а речь на деле об одном оффере — предложи лендинг. Если просит «лендинг», но перечисляет 6 разделов и блог — это многостраничник, скажи об этом прямо.

## Дополнительные вопросы к брифу (шаг 1)

Добавь к `brief.md` блок:

```markdown
## Объём сайта
- Тип: [корпоративный / услуги / каталог / блог / портфолио / смешанный]
- Страницы, которые точно нужны: …
- Динамический контент (блог, новости, каталог): [нет / да — сколько единиц сейчас и как часто растёт]
- Кто и как будет менять тексты после запуска: [разработчик по запросу / владелец сам → нужна админка контента или Markdown-файлы]
- Языки: [один / несколько → hreflang, отдельные юр. тексты]
- SEO: [важен / не важен]; главные поисковые запросы, если есть
- Личный кабинет, оплата, запись онлайн: [нет / да → отдельный проект, а не страница; стоп-флаг «объём»]
```

Личный кабинет, интернет-магазин с корзиной, бронирование с календарём — это уже веб-приложение. Скажи пользователю, что это другой масштаб, и предложи вынести за рамки первой версии.

## Карта сайта → `sitemap.md` (вместо плоской structure.md)

Составляется ДО дизайна, после шлюза 1. Формат:

```markdown
# Карта сайта — [название]

## Дерево страниц
- / — Главная
  - /uslugi/ — Услуги (хаб)
    - /uslugi/<slug>/ — Страница услуги (шаблон «Услуга»)
  - /o-nas/ — О нас
  - /kontakty/ — Контакты
  - /blog/ — Блог (хаб) → /blog/<slug>/ (шаблон «Статья»)
  - Юридические: /privacy/, /consent/, /offer/ (при продаже), /cookies/

## Глубина и навигация
- Максимум 3 клика от главной до любой страницы.
- Главное меню (5–7 пунктов): …
- Подвал: полная карта + юр. документы + реквизиты.
- Хлебные крошки: на всех страницах глубже 1 уровня.

## Для каждой страницы / шаблона
| Страница | Цель | Кто сюда приходит | Главное действие | Ссылки дальше |
|---|---|---|---|---|
```

Правила:
- **Один шаблон на тип страницы.** 8 услуг = один шаблон «Услуга» + 8 наборов контента, а не 8 дизайнов.
- **У каждой страницы одно главное действие** (заявка, звонок, переход глубже). Нет действия — зачем страница?
- **Каждая страница достижима из меню или хаба.** Сирот не бывает.
- Страница без реального контента не создаётся. «Наша команда» без реальных людей, «Отзывы» без реальных отзывов, «Блог» без статей — не делаем (см. запрет на выдуманные доказательства).

### Структура шаблонов → `structure.md`

`structure.md` теперь пишется **на каждый шаблон страницы** (не на каждую страницу): главная, хаб, услуга, статья, контакты. Формат блока — как в `briefs.md`. Для главной используй логику вопросов посетителя; для внутренних страниц — «пришёл из поиска/меню с конкретным вопросом, ответ в первом экране».

## Визуальные направления (шаг 5)

Показывай направления не на одной странице, а на **трёх типовых экранах**: главная, внутренняя страница-шаблон (услуга/статья), контакты/форма. Плюс мобильное меню (открытое состояние) — на многостраничнике оно часть дизайна, а не деталь. Один HTML-файл превью с переключением между экранами. Дизайн-система (токены, типографика, компоненты) в `CHOICE.md` фиксируется **как система**: карточка, кнопка, заголовки H1–H3, состояния ссылок — это будет повторяться на всех страницах.

## Общие компоненты (реализация, шаг 7)

Один источник правды для повторяющегося:
- шапка и мобильное меню (с активным пунктом);
- подвал (карта, реквизиты оператора, юр. ссылки);
- cookie-баннер (грузится на всех страницах; решение пользователя запоминается, не спрашиваем заново на каждой);
- форма заявки как переиспользуемый блок (можно встраивать на любую страницу; в базу пишется **страница-источник** — `source_page`);
- хлебные крошки, карточка, кнопка, CTA-полоса.

## Стек для многостраничника

| Объём | Решение | Почему |
|---|---|---|
| До ~10 страниц, тексты правит разработчик | Статический HTML + маленький `build.py`, который подставляет `partials/header.html`, `footer.html` в каждую страницу | Нет дублирования шапки/подвала, нет фреймворка |
| 10+ страниц, блог/каталог, повторяющиеся шаблоны | Статический генератор (Eleventy или Astro) + Markdown-контент; на выходе — обычная статика для nginx | Новая статья = новый `.md`-файл, шаблоны не копируются |
| Владелец сам редактирует без разработчика | Статический генератор + лёгкая админка контента (Decap CMS и т. п.) **или** честно сказать: «правки через меня» | Не городи CMS, если правки раз в квартал |
| Нужен личный кабинет / магазин | Отдельный проект, не этот скилл | |

Бэкенд приёма заявок, SQLite и админка заявок — как в `stack.md`, без изменений. Отличия:
- `POST /api/lead` принимает поле `source_page` (путь страницы) и `source` (форма/лидмагнит); админка показывает их колонками.
- nginx: чистые URL без `.html` (`try_files $uri $uri/ $uri.html =404`), своя страница `404.html`, `301`-редиректы со старых адресов (если сайт переезжает) — отдельным файлом в конфиге.
- Статику не кэшируй вечно без хэшей в именах файлов: при правке CSS посетители не должны видеть старую вёрстку.

## SEO-основы (для многостраничника это часть поставки)

На каждой странице:
- уникальные `<title>` (до ~60 символов) и `<meta name="description">` (до ~160);
- один `<h1>`, иерархия H2–H3 без пропусков;
- `<link rel="canonical">`; `lang` в `<html>`;
- Open Graph (`og:title`, `og:description`, `og:image`) — иначе ссылки в мессенджерах выглядят сиротливо;
- осмысленные `alt` у изображений, размеры `width/height` (против прыжков вёрстки);
- внутренняя перелинковка: хаб ↔ дочерние страницы, «читайте также» в статьях.

На сайте:
- `sitemap.xml` и `robots.txt` (закрыть `/admin`, `/api`);
- микроразметка JSON-LD: `Organization` на главной, `BreadcrumbList` на внутренних, `Article` на статьях, `LocalBusiness` для услуг с адресом — только с реальными данными;
- в РФ: добавить сайт в Яндекс Вебмастер, в мире — Google Search Console; подтверждение прав на сайт делает владелец;
- не индексировать `/admin`, страницы «спасибо», тестовые копии (`noindex`).

Не обещай позиции в выдаче и не пиши «SEO-оптимизированные тексты» ради ключей: тексты пишутся для человека, а техническое SEO — это пункты выше.

## Юридика на многостраничнике

Принцип прежний, масштаб шире:
- **Согласие и чекбоксы — в каждой форме на каждой странице**, где собираются данные. Форма в подвале и форма на странице услуги — две формы, обе с чекбоксом и ссылками на документы.
- В `legal-map.md` добавь вопрос: **«Какие ещё места сбора данных есть на сайте?»** Подписка на блог, комментарии, форма обратной связи, чат, запись на консультацию, калькулятор с отправкой результата — каждое такое место получает свой вердикт и свою цель обработки в политике.
- Политика конфиденциальности перечисляет **все** формы и цели, а не одну.
- Cookie-баннер: единая настройка на весь сайт; страница «Политика cookie» со списком реально используемых cookie (для ЕС/Великобритании — обязательно по справочнику).
- Подвал на каждой странице: реквизиты оператора, ссылки на политику, согласие, оферту.
- Внешние виджеты (карты, видео, чат, шрифты с CDN) на нескольких страницах — это передача данных третьим лицам. Для РФ — локализация (шрифты и скрипты локально, карты — отечественные или статичное изображение); для ЕС — только после согласия.

## Деплой (шаг 8)

Без изменений, кроме:
- конфиг nginx под чистые URL, 404, редиректы (см. выше);
- после выкладки отправить `sitemap.xml` в Вебмастер/Search Console (действие владельца);
- если сайт заменяет старый — **карта редиректов** старый URL → новый составляется ДО переключения DNS, иначе теряется поисковый трафик;
- Метрика: цели на форму **по каждой странице-источнику** (или один счётчик + `source_page` в базе), плюс цели на ключевые клики (телефон, мессенджер).

## QA многостраничника (шаг 9)

К чеклисту `qa.md` добавь:
- [ ] Каждая ссылка меню, подвала и хлебных крошек открывает существующую страницу (прогнать краулером или скриптом — нет 404 и цепочек редиректов).
- [ ] Нет страниц-сирот: всё из `sitemap.md` достижимо из меню/хаба.
- [ ] Мобильное меню открывается, закрывается, не перекрывает контент после закрытия; активный пункт подсвечен.
- [ ] У каждой страницы уникальные title/description, один H1, canonical.
- [ ] `sitemap.xml` и `robots.txt` отдаются; `/admin` не индексируется.
- [ ] Форма на **каждой** странице, где она есть, прошла сквозной тест: заявка → база (с верным `source_page`) → Telegram → админка; без чекбокса не уходит.
- [ ] Cookie-баннер появляется один раз, выбор сохраняется при переходе между страницами.
- [ ] Страница 404 оформлена и ведёт на главную.
- [ ] Скорость: каждая страница типа (главная, внутренняя, статья) проверена отдельно, первый экран ≲ 500 КБ.
- [ ] Выложенные тестовые страницы/черновики не попали в `sitemap.xml`.

## Передача владельцу

К стандартной передаче добавь инструкцию **«как добавить страницу/статью»**: в какой файл положить текст, какую команду запустить для сборки, как выложить на сервер (или как это сделать через админку контента, если она есть). Если владелец сам этого делать не будет — прямо запиши: «правки вносит [исполнитель], вот как к нему обратиться».
